## 1. `setMaxIter(5)` 和 epoch 的关系

**相似但不完全相同。**

- **深度学习的 epoch**：把整个训练数据集完整过一遍算一个 epoch，每轮用梯度下降更新一次参数。
- **ALS 的迭代**：ALS 的核心思路是**交替优化**——固定用户隐因子去求解物品隐因子，再固定物品隐因子去求解用户隐因子，这样交替进行。**每交替一轮就算一次迭代。**

```
ALS 交替过程（setMaxIter(5) → 共交替5轮）：

第1轮：固定物品因子 → 求解所有用户因子 → 固定用户因子 → 求解所有物品因子
第2轮：同上
...
第5轮：同上 → 结束
```

所以它和 epoch 在"重复训练过程"这个概念上是类似的，但底层机制完全不同。ALS 没有学习率、没有反向传播，而是通过最小二乘法直接求解。

## 2. `setRegParam(0.01)` 正则化

你说得对，正则化主要有 **L1** 和 **L2** 两种：

| | L1 正则化（Lasso） | L2 正则化（Ridge） |
|---|---|---|
| **惩罚项** | 参数的**绝对值**之和 λ∑\|w\| | 参数的**平方**之和 λ∑w² |
| **效果** | 倾向于让部分参数变为**0**（产生稀疏解） | 倾向于让参数**整体变小**，但不会精确为0 |
| **用途** | 特征选择 | 防止过拟合，稳定训练 |

**在 Spark ALS 中，`setRegParam` 设置的是 L2 正则化系数 λ。**

ALS 的优化目标是最小化：

```
min  ∑(r_ui - p_u · q_i)²  +  λ(||p_u||² + ||q_i||²)
      ↑ 预测评分与真实评分的误差     ↑ L2正则项，惩罚过大的隐因子值
```

- **λ = 0**：不正则化，容易过拟合（模型记住训练数据的噪声）
- **λ 过大**：正则化太强，模型欠拟合（隐因子被压得太小，表达力不足）
- **λ = 0.01**：一个比较小的正则化系数，属于常见的起始尝试值

Spark ALS **没有暴露 L1 正则化的选项**，只支持 L2。

## 3. 隐向量的维度

**确实没有显式设置，用的是默认值。**

Spark ALS 中控制隐向量维度的参数是 **`rank`**，**默认值为 10**。

```scala
val als = new ALS()
  .setMaxIter(5)
  .setRegParam(0.01)
  .setRank(10)          // ← 这个没写，默认就是10
  .setUserCol("userIdInt")
  .setItemCol("movieIdInt")
  .setRatingCol("ratingFloat")
```

`rank` 的含义是用户/物品隐因子向量的维度：

```
用户隐因子 p_u ∈ R^rank    （例如10维向量）
物品隐因子 q_i ∈ R^rank    （例如10维向量）
评分预测 = p_u · q_i^T     （10维向量的点积 → 一个标量）
```

- **rank 太小**：模型表达力不足，欠拟合
- **rank 太大**：计算量增大，容易过拟合
- 一般通过交叉验证在 {5, 10, 20, 50, 100} 等值中选取最优

这里没设置，说明直接用了默认的10。如果想调优，应该把它也加入参数网格：

```scala
val paramGrid = new ParamGridBuilder()
  .addGrid(als.regParam, Array(0.01, 0.1))
  .addGrid(als.rank, Array(5, 10, 20))  // ← 加入rank的搜索
  .build()
```

## 4.1 交叉验证参数网格的深入分析

### 当前代码的问题

```scala
val paramGrid = new ParamGridBuilder()
  .addGrid(als.regParam, Array(0.01))  // 只有一个参数值
  .build()
```

这里只给一个正则化参数，**没有比较的意义和价值**。交叉验证 + 参数网格搜索的真正价值在于**自动比较多个参数组合，找到效果最好的那个**。

### 如果只看当前代码，交叉验证唯一的作用

即使只有一个参数值，10 折交叉验证相比前面的单次 `randomSplit` 仍然有一个好处——**评估模型的稳定性**：

```
单次 randomSplit（前面的做法）：
  训练集 80% + 测试集 20%（只切一次）
  → RMSE = 0.87（但这个 0.87 可能刚好是因为这次随机划分"运气好"）

10折交叉验证（只有一个参数时）：
  第1折: RMSE = 0.89
  第2折: RMSE = 0.86
  第3折: RMSE = 0.88
  ...
  第10折: RMSE = 0.87
  → 平均 RMSE = 0.873（更可靠，排除了单次划分的偶然性）
```

但这点意义很有限，**真正有价值的用法是放多个候选值进去做比较**。

### 正确写法应该是这样

```scala
val paramGrid = new ParamGridBuilder()
  .addGrid(als.regParam, Array(0.001, 0.01, 0.05, 0.1, 0.5))  // 多个正则化强度
  .addGrid(als.rank, Array(5, 10, 20, 50))                     // 多个隐因子维度
  .build()
// 总共 5 × 4 = 20 种参数组合，每种做10折验证 → 共训练200次模型
```

然后交叉验证会做的事情：

```
参数组合1: regParam=0.001, rank=5   → 10折平均RMSE = 0.921
参数组合2: regParam=0.001, rank=10  → 10折平均RMSE = 0.895
参数组合3: regParam=0.001, rank=20  → 10折平均RMSE = 0.882
参数组合4: regParam=0.001, rank=50  → 10折平均RMSE = 0.879
参数组合5: regParam=0.01,  rank=5   → 10折平均RMSE = 0.903
参数组合6: regParam=0.01,  rank=10  → 10折平均RMSE = 0.873
参数组合7: regParam=0.01,  rank=20  → 10折平均RMSE = 0.865  ← 最优
参数组合8: regParam=0.01,  rank=50  → 10折平均RMSE = 0.871
...
参数组合20: regParam=0.5,  rank=50  → 10折平均RMSE = 0.956

→ 自动选出最优参数: regParam=0.01, rank=20
→ cvModel.avgMetrics 中存储了这20个平均RMSE
```

这才是交叉验证 + 参数网格搜索的完整价值：**自动比较所有参数组合，找到效果最好的那个。**

### 总结对比

| | 当前代码（只有一个值） | 正确用法（多个值） |
|---|---|---|
| **能不能跑** | 能跑，不会报错 | 能跑 |
| **有没有比较** | 没有，无法选优 | 有，自动选最优参数组合 |
| **实际意义** | 仅展示用法，相当于模板代码 | 真正的超参数调优 |

所以当前代码中的参数网格搜索是个**"架子"**，需要补充多个候选值才能真正发挥作用。

## 5. model.setColdStartStrategy("drop") 这个注释我还没看懂，你再说详细一点

## 冷启动问题详解

### 问题是什么？

ALS 模型通过学习得到**每个用户**和**每部电影**的隐因子向量。但测试集中可能出现**训练集中从未出现过的用户或电影**，模型没有学过它们的隐因子，自然无法预测评分，结果就是 **NaN**（Not a Number，非数字）。

举个具体例子：

```
训练集中有 1000 个用户，模型学到了这 1000 个用户的隐因子向量
测试集中出现了 userIdInt = 2001 的用户，但这个用户在训练集中从未出现过
→ 模型根本没有 2001 号用户的隐因子
→ 无法计算 p_u · q_i^T
→ 预测结果 = NaN
```

电影也一样：

```
训练集中有 500 部电影，模型学到了这 500 部电影的隐因子向量
测试集中出现了 movieIdInt = 999 的电影，但训练集中没有这部电影
→ 模型没有 999 号电影的隐因子
→ 预测结果 = NaN
```

### 这对评估有什么影响？

如果不处理，`predictions` 预测结果里会混入 NaN：

```
| userIdInt | movieIdInt | ratingFloat | prediction |
|-----------|------------|-------------|------------|
| 1         | 101        | 4.0         | 3.8        |
| 2         | 102        | 3.0         | 3.2        |
| 2001      | 101        | 5.0         | NaN        |  ← 冷启动用户
| 1         | 999        | 2.0         | NaN        |  ← 冷启动电影
```

然后把这个带 NaN 的结果喂给 `RegressionEvaluator` 计算 RMSE 时：

```
RMSE = sqrt(∑(真实评分 - 预测评分)² / N)

其中 (5.0 - NaN)² = NaN
→ 整个求和结果变成 NaN
→ RMSE = NaN
→ 评估指标完全失效，无法衡量模型好坏
```

### `setColdStartStrategy` 的两个选项

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `"nan"`（默认） | 冷启动用户的预测结果保持 NaN 原样返回 | 你不需要评估，只是做预测 |
| `"drop"` | 在计算评估指标时，**自动丢弃**所有预测为 NaN 的行 | 你需要用 RMSE 等指标评估模型 |

代码里加了 `"drop"` 后的效果：

```
丢弃前：
| userIdInt | movieIdInt | ratingFloat | prediction |
|-----------|------------|-------------|------------|
| 1         | 101        | 4.0         | 3.8        |
| 2         | 102        | 3.0         | 3.2        |
| 2001      | 101        | 5.0         | NaN        |  ← 被丢弃
| 1         | 999        | 2.0         | NaN        |  ← 被丢弃

丢弃后（只用于评估计算）：
| userIdInt | movieIdInt | ratingFloat | prediction |
|-----------|------------|-------------|------------|
| 1         | 101        | 4.0         | 3.8        |
| 2         | 102        | 3.0         | 3.2        |

→ RMSE = sqrt(((4.0-3.8)² + (3.0-3.2)²) / 2) = sqrt(0.04+0.04)/2) ≈ 0.2
→ 得到一个有效的评估指标
```

### 一句话总结

**`setColdStartStrategy("drop")` 的作用就是：在评估模型时，遇到模型从未见过的用户或电影导致预测结果为 NaN 的情况，自动把这些 NaN 行扔掉，保证 RMSE 等评估指标能正常计算出有意义的数值。**

## 6. 交叉验证的时间复杂度分析

**你的思考完全正确！** 交叉验证的时间复杂度确实是指数级增长的：

```
模型训练总次数 = 参数组合数 × 折数

当前代码（1个参数值）：
  regParam: [0.01] → 1种组合
  10折交叉验证 → 每种组合训练10次
  总训练次数 = 1 × 10 = 10次

如果扩大搜索范围：
  regParam: [0.001, 0.01, 0.05, 0.1, 0.5] → 5种
  rank: [5, 10, 20, 50] → 4种
  总参数组合 = 5 × 4 = 20种
  10折交叉验证 → 每种组合训练10次
  总训练次数 = 20 × 10 = 200次

时间估算（假设单次训练1分钟）：
  当前代码：10分钟
  扩大搜索：200分钟 ≈ 3.3小时
```

### 交叉验证配置开关

代码中已经添加了 `ENABLE_CROSS_VALIDATION` 配置开关：

```scala
val ENABLE_CROSS_VALIDATION = false  // 设为true才会执行交叉验证

if (ENABLE_CROSS_VALIDATION) {
  // 执行耗时的交叉验证调参
  val cv = new CrossValidator().setNumFolds(10)...
} else {
  println("跳过交叉验证调参")
  println(s"当前模型RMSE: $rmse")
}
```

**使用建议：**
- 如果只需要快速训练模型并保存embedding，设置 `ENABLE_CROSS_VALIDATION = false`
- 如果需要评估模型效果或进行超参数调优，设置 `ENABLE_CROSS_VALIDATION = true`
- 建议先用小参数范围测试，确认代码无误后再扩大搜索范围
